# Failure recovery — Phase 4

Use during VERIFY/REVIEW in the [protocol](EXECUTION_PROTOCOL.md); results use its four labels. Preserve sanitized evidence before recovery. A failed execution does not establish that application code is defective. Fix within authorized scope, rerun affected checks after a justified change, and keep first-attempt evidence alongside the recovery result. Stop only the dependent edit/check when blocked and continue independent useful work.

| Case / identification | Evidence to preserve | Safe recovery | Stop condition and incomplete report |
| --- | --- | --- | --- |
| Test failure: assertion, runner error or nonzero exit | Exact command/cwd/patch, failing test/input/expected/actual, runner output, fixture/request timing and first failure | Isolate cause; reproduce a focused case, correct the actual owner or demonstrated fixture race, then rerun focused and applicable baseline checks | Stop speculative fixes when cause cannot be established or needs unauthorized data/tool changes. Attempt Failed; unresolved behavior Not verifiable; name next discriminating step |
| TypeScript error: diagnostic or typegen/compiler nonzero | Command, diagnostic code/file/line, current imports/types, exit and generated-file delta | Trace contract/types at owner; use supported existing typegen when appropriate; fix scoped error | Stop if contract authority is missing or correction expands scope. Attempt Failed; type safety not established. No broad casts, ts-ignore or disabled type checks |
| Lint failure: rule diagnostic/nonzero | Rule, location, command/config identity and output | Correct the owning code within architecture; distinguish pre-existing diagnostics using initial source evidence | Stop if only workaround would weaken rules or alter unauthorized config. Attempt Failed; explain pre-existing versus introduced only when demonstrated |
| Architecture violation: scanner reports boundary/cycle/server reachability | Complete reported import path/cycle, owner, public entries and exact scanner output | Correct the dependency/composition through existing public entries; rerun scanner and other affected gates | Stop if a new architecture decision or sibling edit is required. Attempt Failed; no scanner relaxation or broad re-export |
| Production build hangs/timeouts: no completion or budget exceeded | Build command/bundler/config, elapsed time, last output, process identity, exit/signal or unknown, resource observations and partial artifacts | Set a justified bounded time budget before starting, based on available prior timings and resources. ## Recovery discipline

A rerun has a new evidence ID; a later Passed result does not erase the initial Failed attempt. For an unchanged flaky case, state the isolating hypothesis and why a bounded rerun provides new information. Do not keep retrying unchanged stalled builds, raise timeouts blindly, weaken assertions, change build/CI configuration or install tools as a workaround without authorization. Existing mandatory gates remain in [VALIDATION.md](VALIDATION.md).

After recovery, inspect task-generated artifacts, preserve user work, rerun affected gates and self-review the final delta. If unresolved, state Implementation Complete according to actual edits, Verification Complete: No and Delivery Ready: No for a target requiring that check; include blocker, evidence, safe next step and task-only rollback. An incomplete application check from a prior experiment stays incomplete; documentation validation does not repair it.
